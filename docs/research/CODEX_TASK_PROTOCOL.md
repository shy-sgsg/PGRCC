# Codex 科研任务协议

本协议规定 Codex 如何把一次科研任务放回 PGRCC 的长期研究框架中。长期研究目标和方向以[研究总纲](RESEARCH_MASTER_PLAN.md)为准；最新进展以[动态研究状态](RESEARCH_STATUS.md)为准；已经作出的方向决定见[研究决策日志](RESEARCH_DECISION_LOG.md)。本协议不另立研究主题。

## 1. 启动前的强制阅读顺序

先按仓库规范检查分支和工作树，保护已有改动。每次科研任务都必须首先读取当前工作分支版本的 `docs/research/RESEARCH_MASTER_PLAN.md`。随后按顺序读取：

1. `docs/research/RESEARCH_STATUS.md`；
2. `docs/research/RESEARCH_DECISION_LOG.md`；
3. `docs/research/CHATGPT_REVIEW_PROTOCOL.md` 与 `AGENTS.md`；
4. 相关阶段计划、阶段证据导航、报告和最小充分的历史证据；
5. 本任务直接涉及的源码、配置、数据、脚本与运行记录。

不得只依据最近一份报告、TODO、短期计划或用户最后一句话机械安排研究任务。用户的最新明确指令可以调整本次执行优先级，但不表示已经批准修改长期总纲。

## 2. 任务定位与价值判断

科研实施计划应在开头简要写明：

- **依据版本：** 总纲路径及其 Git commit / blob 版本，动态状态和决策日志版本；
- **总体目标：** 本任务服务于总纲中的哪个长期目标或研究模块；
- **具体科学问题：** 本次要回答什么问题；若是工程维护，说明它如何影响研究链路可信度；
- **已有证据：** 已确认结论、未验证假设及关键替代解释；
- **研究必要性：** 为什么现在值得做，是否有更简单且足够的传统方法；
- **评价标准：** 哪些证据可以支持任务完成，哪些项目可能 `NOT_EVALUABLE`；
- **停止条件：** 哪些结果要求停止、暂停或提交方向调整建议；
- **预期贡献：** 工程基础、物理机制解释、评价证据或潜在算法创新。

对普通维护或文档任务可简化科学问题与贡献说明，但不得完全忽略总纲；若任务与科研主线无关，应明确这一点。若发现原假设已被否证、问题可由常规工程方法充分解决、指标不可评估、方法没有任务收益或工作偏离总纲，应停止受影响的工作并记录证据，不为执行旧计划继续消耗资源。

## 3. 执行、更新与边界

- 按当前任务所需的最小充分方案执行，保留失败和不确定性，不把计划、测试、历史数据或 CPU 结果写成未执行的 CUDA Production 证据。
- 阶段进展、当前唯一优先任务、已停止假设和未决问题写入 `RESEARCH_STATUS.md`；新的方向裁决按追加方式写入 `RESEARCH_DECISION_LOG.md`；阶段设计、执行和结果留在对应阶段材料中。
- 动态文件必须采用总纲既定的主题和目标。若新证据与总纲冲突，应记录冲突并提交用户讨论，不得借状态文件、决策日志或阶段报告暗中重定义长期方向。
- 任何对 `docs/research/RESEARCH_MASTER_PLAN.md` 正文的修改都必须在编辑前取得用户针对具体内容或清晰范围的明确批准。阶段 `CONTINUE / STOP / PIVOT`、一般任务指令、ChatGPT 建议和自动提交/推送权限均不是批准。未经批准时，总纲必须保持无差异。
- 经批准的总纲修改须记录日期、修改前后版本、用户批准范围、依据、受影响目标/成果和后续影响；不得扩大用户批准范围。

## 4. 阶段结束与汇报

具有科研意义的阶段结束时，先向用户给出简洁结论，再提供可独立核查的审查材料。使用[ChatGPT 审查请求模板](templates/CHATGPT_REVIEW_REQUEST.md)，包含仓库、分支、完整审查 commit、总纲版本、动态状态版本、实验执行源码 commit（如不同）、研究目标、科学问题、执行身份、关键结果、限制、方向判断和证据入口。不得以“最新提交”或“当前 HEAD”替代完整 SHA。

审查请求开头必须提示 ChatGPT 先读取该提交对应版本的研究总纲，并要求它同时审查阶段任务正确性和总体科研价值。提交或推送授权只覆盖已审查且已授权的变更，不扩大总纲修改权限。
