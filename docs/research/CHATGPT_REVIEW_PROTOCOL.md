# PGRCC ChatGPT 科研审查规范

## 1. 目的

ChatGPT 审查既检查阶段工作是否做对，也独立判断它是否值得继续、是否服务于总体 GMTI 研究目标，以及是否应 `CONTINUE / STOP / PIVOT`。阶段报告通过、测试通过或 CUDA 运行成功，都不能自动证明科学问题重要、方法有创新或任务性能有收益。

本规范与 [研究总纲](RESEARCH_MASTER_PLAN.md)、[动态研究状态](RESEARCH_STATUS.md) 和 [研究决策日志](RESEARCH_DECISION_LOG.md) 配套使用。研究总纲是 PGRCC 最高层级科研指导文件，定义长期主题、总体目标、核心科学问题、研究内容、总体思路、长期技术路线及评价边界；动态状态记录最新阶段和短期任务；决策日志追加方向决定。动态状态或阶段裁决不得取代总纲中的长期目标。若总纲现有序言对“最新决策记录”有其他表述，不应将其解释为可绕过用户批准的总纲覆盖权；在相应修改获批前，总纲长期目标仍具指导效力。

任何对 `docs/research/RESEARCH_MASTER_PLAN.md` 正文的修改都必须在编辑前获得用户针对具体内容或清晰范围的明确批准，包括错字、标题、链接、状态、当前任务和建议。ChatGPT 的结论只能是修改建议，不能视为批准；未获批准不得直接修改或通过其他文件暗中取代总纲。若建议修订，应给出证据、原文问题、拟改范围、替代方案及对既有目标和成果的影响，交由用户讨论。

## 2. 每次审查前必须读取

正式审查必须针对用户指定的仓库、分支与完整 Git commit SHA。若审查快照已提供，所有文件优先从该快照读取；远端 HEAD 仅用于核对是否发生变化，不得替代指定快照。第一份研究文件必须是该 commit 对应版本的研究总纲。按以下顺序读取：

1. `docs/research/RESEARCH_MASTER_PLAN.md`：完整理解长期主题、目标、科学问题、研究内容、总体思路和技术路线；
2. `docs/research/RESEARCH_STATUS.md`：确认当前动态阶段、近期结论、未决问题和任务状态；
3. `docs/research/RESEARCH_DECISION_LOG.md`：追踪已作出的方向决定及其证据；
4. `AGENTS.md`、`README.md` 和本审查规范：核对工程安全、研究治理和审查边界；
5. [Phase R 证据导航](phase_r/README.md)及本次实验设计、结果报告和方向裁决；
6. 结论所依赖的代码、配置、脚本、manifest、日志、数据身份和核心评价产物；
7. 会改变本次判断的必要历史阶段证据。

不要求无差别阅读仓库内所有文件或大型原始数据。应先依据阶段报告定位源文件和关键证据，再核对决定性主张。必须说明实际读取的 commit、文件/产物与审查范围。若仓库、分支、commit 或输入不可访问，列出具体缺失项，将相关结论标为 `NOT_VERIFIED`；不能假称已经阅读，也不能仅凭用户贴出的最后一份报告安排下一阶段。

若指定 commit 或总纲文件无法读取，可以继续审查已提供的阶段材料，但必须明确列出未读文件，并将总体研究价值、方向一致性和总纲合理性审查标记为 `NOT_VERIFIED`。不得用 Codex 的摘要代替总纲原文。

## 3. 两层审查

### A. 阶段任务正确性

检查实验假设与配对设计、物理单位/坐标/符号、代码数据流、配置与运行时生效值、输入和源码身份、是否真实执行指定后端、目标/真值泄漏、统计单位与分子分母、任务关联、失败样本、可复现命令以及结论边界。

按适用性区分：

- `IMPLEMENTED`：实现或配置存在；
- `EXECUTED`：指定路径确实运行并有可追溯运行记录；
- `EVALUABLE`：该项有有效输入、分母、truth/关联和指标定义；
- `PERFORMANCE_VERIFIED`：足够的独立重复及任务评价支持限定范围的性能主张。

软件测试、CPU 模拟、历史数据、仅编译、产物存在或退出码为 0，不能替代真实 CUDA Production 证据。若本次不要求 CUDA，明确区分“本次未运行”与历史运行。

### B. 总体科研价值与方向

阶段任务正确完成与否，不能代替总体科研价值判断。必须独立检验阶段成果是否推动长期目标，并审查总纲中的科学问题、长期路线和创新性边界是否仍符合最新证据。至少回答：

- 本阶段解决的科学问题是否真实、重要并与总纲一致？
- 是否识别了与物理边界、系统模型、算法或评价实现对应的具体机制？
- 是否有公平且足够强的传统 Baseline？不同观测信息/自由度是否分层？
- Known-error correction upper bound 与实际 Estimated correction 之间还有多少有任务意义的可恢复空间？
- 观察到的收益是否属于最终 GMTI 任务，而非仅中间 SCNR、残差或软件正确性？
- 是否存在更简单、已知的校准/统计/信号处理方法能够解决问题？
- 研究是否仍有清晰的论文贡献，或已经被常规工程标定/现有方法解决？
- AI 是否确有必要，还是只是可选工具？若讨论 AI，部署输入、信息泄漏、泛化与强确定性基线是否公平？
- 低速、复杂杂波、有限样本、系统失配、目标保持、测角定位或速度估计中，哪些有证据，哪些只是待查假设？
- 当前应 `CONTINUE`、`STOP` 还是 `PIVOT`？什么具体证据会改变该判断？
- 总纲所定义的问题、路线或模块优先级是否需要用户重新讨论？若是，给出具体证据、原方案局限、替代方案、科学意义及对既有成果的影响；这只是建议，不是修改授权。

批评应基于可定位证据，不为显得严格而制造新方向。

## 4. 证据和文献规则

将以下内容分别标注，不要混写：

1. **仓库观测证据：** 当前源码、当前配置/输入、本次或明确身份的历史运行产物；
2. **理论推导：** 明示假设、适用范围和未建模因素；
3. **外部文献：** 论文的系统、数据、方法、Baseline 和指标适用条件；需要外部检索时优先找一手论文、官方技术资料或公开数据原始来源；
4. **分析推论：** 从上述证据推导的可能解释；
5. **未验证设想：** 仅作为候选，不写成结论。

文献中的改善幅度不能直接外推为 PGRCC 收益。文献未取得全文时，说明只依据摘要/可访问内容；不把综述性描述、摘要或仿真结果说成实飞验证。

## 5. 完整审查的固定输出

每次完整阶段审查至少按此顺序给出：

1. **审查范围与身份：** 仓库、branch、commit、实际访问到的材料和限制；
2. **阶段任务是否可信：** 物理/代码/数据/指标/信息隔离/复现各项判断；
3. **状态表：** 对核心结论逐项标出 `IMPLEMENTED / EXECUTED / EVALUABLE / PERFORMANCE_VERIFIED`；
4. **相对总纲的进展：** 本阶段补上了哪块证据，如何改变决策；
5. **不能支持的结论：** 明确区分未运行、不可评估、样本不足和结果为负；
6. **物理、算法、评价和比较问题：** 按能否改变主结论排序；
7. **科研价值：** 该工作实际贡献、可能的新颖性、工程常规解法及反例；
8. **方向一致性：** 总体主题、目标、模块和路线是否需要调整；
9. **方向裁决：** `CONTINUE / STOP / PIVOT` 三选一，并给证据和停止条件；
10. **下一步唯一优先任务：** 单一、有限、可改变决策的任务，说明输入、交付和验收门；
11. **改变判断的关键结果：** 什么观测会使推荐转向另一个决定；
12. **待修正文档/决策：** 是否要追加决策日志；如建议修改总纲，列出具体提案和影响，并明确等待用户批准，不能直接编辑。

如果总方向无需调整，也必须说明为什么。不要把一份长待办清单伪装成“唯一下一步”。

## 6. 可复制的完整审查提示词

```text
你是 PGRCC 项目的独立科研审查者。请审查我提供的阶段成果，并同时判断本阶段是否值得继续、是否服务于整个 GMTI 研究课题。不要只做代码审查，也不要因为测试或仿真运行通过就默认研究方向正确。

仓库：https://github.com/shy-sgsg/PGRCC
目标分支：[填 branch]
目标 commit：[填完整 commit SHA；如审查工作树，另附 diff]
待审阶段/任务：[填阶段名、目标、指定报告]
本次变更摘要：[填摘要或提供 git diff]

开始审查前，必须先读取本次审查 commit 对应版本的 docs/research/RESEARCH_MASTER_PLAN.md，并完整理解 PGRCC 长期研究主题、总体目标、核心科学问题、研究内容、总体研究思路和长期技术路线。随后按顺序读取：
1. docs/research/RESEARCH_STATUS.md；
2. docs/research/RESEARCH_DECISION_LOG.md；
3. AGENTS.md、README.md 和 docs/research/CHATGPT_REVIEW_PROTOCOL.md；
4. docs/research/phase_r/README.md；
5. 本阶段设计、执行/结果报告、方向决策及其引用的配置、源码、脚本、manifest、日志和关键评价产物；
6. 若会改变结论，再读取必要的历史证据。

如果指定 commit 或研究总纲无法实际读取，逐项说明并将总体研究目标一致性、方向合理性和总纲本身审查标为 NOT_VERIFIED。不得假称读过，也不得用 Codex 摘要替代总纲。

先报告你实际读到的 branch、commit 和文件。如果 GitHub、commit、输入或产物不可访问，逐项列出；将依赖缺失材料的判断标为 NOT_VERIFIED。不要假称读过，也不要仅根据最后一份报告决定下一阶段。无需无差别读取所有文件或超大原始数据；请沿关键主张追溯到最小充分源码和产物。

请完成两层审查。第一层判断阶段任务是否正确完成；第二层独立判断科学问题价值、长期目标一致性、方向合理性、替代路线和总纲是否仍符合最新证据。阶段测试通过或结果改善不能自动证明总体方向正确或具有创新价值。

A. 阶段任务正确性：
- 检查实验设计、物理模型、单位/符号/坐标、生产处理链与实际运行时配置；
- 检查源码/二进制/输入身份、配对关系、失败分支、truth/未来信息/配对参考泄漏；
- 核对指标定义、分子分母、有效 CUT、最终唯一 hit-cell、H0 false-hit、truth association、参数可评估性和统计单位；
- 区分真正的 CUDA Production、CPU/离线分析、软件测试、历史结果和未执行计划；
- 检查目标保持、检测与错误输出、角度/位置/径向速度/地速、航迹及复杂度，避免用单一中间指标代替任务结果；
- 判断每条关键结论分别属于 IMPLEMENTED、EXECUTED、EVALUABLE 还是 PERFORMANCE_VERIFIED，并给证据路径/行号或 manifest 字段。

B. 总体科研价值与方向：
- 先结合已读取的研究总纲回答，本阶段对 GMTI 课题实际贡献了什么；
- 独立判断问题是否真实、有任务影响、物理上可恢复且有论文研究价值；
- 审核与 Current CSI、普通相减、SCC、DDC、Robust DDC 和其他适用强传统 Baseline 的公平对照；不同输入信息/空间自由度必须分开或匹配；
- 量化或解释 Known-error correction upper bound、Current+unknown-error 与 Estimated correction 的差距；检查符号和指标方向；
- 判断问题是否已由普通标定、信号处理或已有传统方法解决；也要指出现有证据是否不足以支持该判断；
- 不要预设低速目标、复杂杂波、系统失配或 AI 是当前胜出主线。逐项区分已证事实、未闭合评价、理论可能与待检假设；
- “做对了”不代表“值得继续”。请从论文贡献、替代解释、最简单解决方案、泛化、工程代价和失败可能性主动挑战当前假设；
- 独立检查研究总纲所定义的科学问题、技术路线和创新性边界是否仍符合最新证据；如建议调整，说明具体依据、替代方案及对既有成果的影响，并提交用户讨论；
- AI 仅在稳定任务退化、Known 有可恢复空间、确定性强基线留下任务相关残差、实际可用输入且无泄漏、独立场景超过强非 AI 方法时才考虑。不要把 AI 论文存在、Router 历史结果或模型复杂性作为必要性证据。

证据规则：明确区分仓库观察、理论推导、外部一手文献、分析推论和未验证设想。外部检索若会影响方向判断，请检索近期一手论文/官方资料并给可核对链接；说明系统、数据、方法、Baseline 和适用条件。不得把文献增益当成本仓库结果，也不得把摘要级信息说成全文结论。

请严格用以下 12 节输出：
1. 审查范围和代码/数据身份；
2. 阶段结果是否可信；
3. IMPLEMENTED / EXECUTED / EVALUABLE / PERFORMANCE_VERIFIED 状态表；
4. 相对研究总纲的实际进展；
5. 当前结果不能支持什么；
6. 物理、算法、数据、指标和公平比较问题（按严重性排序）；
7. 当前工作的科研价值、新颖性与更简单的替代方案；
8. 是否要调整总体主题、目标、模块或技术路线；
9. 明确给出 CONTINUE / STOP / PIVOT，并说明证据、停止条件；
10. 下一步唯一优先任务（输入、交付、验收/停止门）；
11. 哪个关键实验结果会改变你的建议；
12. 需要追加到 RESEARCH_DECISION_LOG.md 的内容；如建议修改 RESEARCH_MASTER_PLAN.md，列出具体建议、依据和影响，并注明必须等待用户对该修改范围明确批准后才可编辑。ChatGPT 无权将自己的建议视为批准或直接修改总纲。

如果无法判断，请说明缺哪条证据以及最小的判别工作；不要用“再多跑一些实验”代替设计。除非指定，不要建议马上训练 AI、重跑完整 Baseline 矩阵或启动未经授权的 CUDA 阶段。
```
